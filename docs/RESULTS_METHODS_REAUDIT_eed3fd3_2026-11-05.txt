CONFIRMED REMAINING FINDINGS

1. [P2] Metric-row input identity is optional despite mandatory manifest hashes.
   code/evaluation/verify_production_results.py:771-798 checks fake_sha256,
   real_sha256, support_sha256 and real_file only when those CSV columns exist.
   The required schema does not require them, so dropping every identity column
   still yields lineage PASS with a valid manifest and completion records.
   Actual positive-control derivative: remove row identity columns, change a
   finite registered CT, and update its manifest real_sha256. The old perfect
   metrics and old run ID remain unchanged, yet lineage still passes. The current
   manifest matches disk, but the metric rows no longer identify their scored input.
   Required repair: mandate the producer's per-row file/hash identity schema and
   verify it against manifest/current inputs; preserve explicit absent-support
   semantics. Validate run/input identity using the actual evaluator contract,
   without treating the matching run-ID string alone as proof of re-evaluation.
   The producer permits absent-support fallback, so absence of support alone is
   not reported as a separate defect. A support-removal probe in the evidence is
   another identity-boundary check, not proof that fallback itself is invalid.

2. [P2] Completion records are not checked against individual manifest ownership.
   verify_production_results.py:826-854 validates global counts, worker range,
   status and aggregate coverage, but never derives each worker's expected cases
   from manifest items' worker_id assignments. Subject lists are optional.
   Actual counterexample keeps all cohort/file hashes valid and declares two
   workers in the manifest, assigning both cases to worker 0. Sidecars claim one
   assigned/scored case for worker 0 and one for worker 1. Global totals agree,
   so the verifier accepts contradictory per-worker completion evidence.
   Required repair: derive exact per-worker subject sets and counts from the
   manifest and verify each corresponding completion record/shard. Check row
   ownership and zero-error successful completion together, reusing the strict
   merge contract rather than a weaker count-based approximation.

3. [P2] Legitimately idle workers are rejected by the verifier.
   verify_production_results.py:837 rejects num_assigned<=0. The evaluator
   explicitly emits a completed schema-bearing empty shard for idle workers
   (evaluate_synthesis.py:820-844), with assigned=0/scored=0/error_count=0.
   Actual two-case/three-worker execution produces assignment counts [1,1,0].
   Its real strict merge succeeds, but production-verifier lineage fails.
   Required repair: permit zero assignments only when that worker has an empty
   expected assignment set in the manifest, while requiring its completion record
   and all other worker/row proofs. This affects supported small/heavily sharded
   cohorts; no currently running large production cohort was shown to fail.
