CONFIRMED FINDING

1. [P2] Worker repartition of a named run double-counts cases in cohort means.
   code/project10/evaluation/evaluate_synthesis.py:776-804 resumes hash-valid
   cached rows without limiting them to the worker's current assignment.
   Reusing an explicit run ID while changing total_workers can therefore leave
   a previously assigned case in one worker's CSV while its newly assigned
   worker also evaluates it. Manifest checks require expected cases to be
   present but do not reject unexpected cases in a shard; metadata permits
   num_scored greater than num_assigned.

   The merge rewrite validates conflicting duplicates at 503-525 but removed
   the former deduplication of identical Subject rows. Final sort/write around
   589 and summary aggregation retain them, giving those cases extra weight.

   Two independent actual, unmocked workflow probes confirmed the regression:
   - Create cases A, B and C with L1 scores 1, 3 and 5.
   - Evaluate with two workers using an explicit --run_id.
   - Rerun the same inputs/output/run ID with three workers, then perform
     the normal verified merge. No CSV data or metadata is edited.
   - Merge publishes five rows for three unique cases: A, B, B, C, C.
     The reported mean is 3.4 instead of the correct case mean 3.0.

   Restrict resumed records to the current assigned subject set. Require exact
   shard ownership/counts rather than subset presence and scored>=assigned.
   Reject unexpected cross-shard duplicates or deduplicate identical records
   before aggregation, while continuing to reject conflicting evaluations.
   Alternatively reject reuse of a run ID with a changed immutable assignment
   manifest. Test a real repartition/resume flow, not only hand-built conflicts.
